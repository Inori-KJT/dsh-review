# T8 评测集与基线验证报告

2026-11-26 · 执行者：本会话

**结论：评测机制建成并通过验收，基线数据出来了，但最重要的发现不是指标本身，而是——同一个用例连跑两次，命中结果不同。这一条改变了评测的做法。**

## 一、机制：三个新文件

| 文件 | 作用 |
|---|---|
| `src/app/eval.ts` | 用例模型、挖掘算法、命中判定、四个指标、报告渲染。全部纯函数 |
| `scripts/mine.mjs` | 挖掘脚本：读 git 历史，产出候选 JSON 与一份 Markdown 清单 |
| `spike/t8/index.js` | 评测运行器：对每个用例跑一次真实评审，算指标，写基线报告 |

挖掘与评测分开，因为它们的耗时差两个数量级：挖掘是纯 git，几秒；评测要起真实会话，分钟级。先看候选清单再决定跑哪些。

---

## 二、挖掘在真实仓库上得到 0 个候选，原因清楚

对 `TokensService/tokens-worktable`（1815 个提交）实测：

| 项 | 数量 |
|---|---|
| 总提交 | 1815 |
| 以 `Revert` 开头 | **1** |
| 提交主题含"修复" | 132 |
| 以 `fix` 开头 | 223 |
| 含 `introduced by` | **0** |

任务书设想的两种来源在这个仓库里几乎不存在：

- **revert 只有 1 个**，样本量不足以构成缺陷集。
- **修复提交不点名引入者。** 这个仓库的提交习惯是 `[US2026110600346] 修复工作台发行构建的 EvalTokens 拉取认证`——它说修了什么，不说这次修的是哪个提交引入的。

我的挖掘算法要求修复提交**点名**引入它的那个 sha。不点名的我一律不采信，因为"这次修的是哪个提交引入的问题"无法从文本可靠推断，猜错会让缺陷集写成假的。

**所以 60 个提交跑出 0 个候选，不是算法错，是这个仓库的历史里没有可用的信号。** 这一点必须写清楚：如果照这个结果说"评测跑不了"，那是误判——机制是通的（单测覆盖了两类来源各一个正例、一个反例），只是这个仓库喂不出料。

出路正是附录预料到的那条：**改用"注入已知缺陷"的用例集**。

## 三、实际使用的用例集

三个用例，都是真 git 仓库、都有真实的 base/head 两个提交：

| 用例 | 来源 | 缺陷 | 提示位置 |
|---|---|---|---|
| `inj-logic` | injected | 循环条件 `i <= items.length` 越界 | `lib/order.js:5` |
| `inj-security` | injected | 去掉文件名校验后 `path.join` 可穿越 | `lib/report.js:7` |
| `clean-sum` | clean | 无（只是加参数校验） | — |

注入用例的做法：仓库初始提交是正确版本，第二个提交把缺陷注入进去。这样 base/head 都是真提交，走的是与真实 PR 完全相同的代码路径。

## 四、两次评测，结果不同

同一份配置、同一批用例、同一个档位（quick），连跑两次：

| 用例 | 第一次 | 第二次 |
|---|---|---|
| `inj-logic` | 命中 1/1 | 命中 1/1 |
| `inj-security` | **命中 1/1** | **命中 0/1（漏了）** |
| `clean-sum` | 0 条 | 0 条 |
| **已知缺陷命中率** | **100%** | **50%** |
| 干净集误报数 | 0.00 | 0.00 |
| 成本 | 5 会话 / 134 秒 | 4 会话 / 77 秒 |

第一次的 `inj-security` 报出的是"路径穿越"并命中；第二次那条根本没被提交上来。

**这是本次最重要的发现。** 它意味着：

1. **单个用例跑一次的结果不能作为基线。** 50% 与 100% 的差别不是配置改动造成的，是模型自身的不确定性。
2. **比较两版配置时，必须每版各跑多次，比均值与离散度。** 否则会拿噪声当改进。
3. 任务书里"分数不升就不上线"这条判据需要补一个前提：分数必须是多次运行的均值，且样本量足够。

建议写进任务书：**每个用例至少重复 3 次，报均值；两版配置的差小于一个标准差时不算差异。**

## 五、成本数据与预算表对照

实测（quick 档，每个用例一次）：

| 用例 | 会话 | 回合 | 耗时 |
|---|---|---|---|
| inj-logic | 2 | 2 | 39 秒 |
| inj-security | 1 | 1 | 24 秒 |
| clean-sum | 1 | 1 | 15 秒 |

对照预算表 Quick 档：会话上限 2、token 上限 40 万、时间上限 10 分钟。**会话数与时间都远在限内**（最快 15 秒，最慢 39 秒，上限 600 秒）。

另有一个更重的真实数据点来自 T6：Standard 档在真实 PR 上 **376 秒、0 条发现**。Standard 的时间上限是 25 分钟，实测用量约为上限的四分之一。

**结论与建议：**

- **Quick 档的时间上限 10 分钟偏松**，实测最慢 39 秒。建议收紧到 3 分钟，这样超时能更早暴露问题。
- **Standard 档的 25 分钟上限与实测 376 秒相比也偏松**，但真实 PR 的差异幅度未知（一次样本不够），暂不调整，等 T9 有更多样本再定。
- **token 数仍然取不到**，预算表里那一列无法校准。这是宿主侧的能力缺口，不是本引擎的疏漏。

## 六、顺手修掉的三个问题

### 6.1 回合数一直是 0

`runs.usage.turns` 从 T3 起就写死为 0。补了两处：`BudgetUsed` 增加 `turns` 字段并在 `charge()` 里累加；`runPipeline.finish()` 改用真实值。同时 `buildDeps` 增加了 `turnCounter` 注入点——不注入时它仍是 0，因为回合数只有宿主能数。

修完后实测回合数变为 2 / 1 / 1，与 `stage_execs` 的增量记录一致。

### 6.2 本地评测被令牌卡住

`buildDeps` 无条件构造 GitCode 客户端，于是**跑本地仓库的评测也要先准备平台令牌**。改成可注入 `forge`，评测传一个空实现即可。

### 6.3 `.js` 文件里不能用内联类型导入

`spike/t8/index.js` 是 `.js`，Node 不对它做类型剥离，所以 `import { a, type B }` 直接报 `Unexpected identifier 'B'`。已改成只导入实际用到的值。

**这条要写进 `AGENTS.md`：本项目里 `.ts` 与 `.js` 的语法边界不同，`.js` 文件禁止任何 TypeScript 语法。**

## 九、遗留与下一步

**遗留一，基线样本量太小。** 3 个用例、每个跑 1 次。真正的基线需要每个用例重复 3 次以上，且缺陷集规模在 15 到 20 个。本次受时间限制只做了机制验证。

**遗留二，挖掘算法需要适配这个仓库的提交习惯。** 现在只认"点名引入者"的修复提交。可行的替代是：把"改动的行与某个更早提交改动的行重叠"作为候选，交人工确认。但这会引入更多假候选，人工成本上升，需要先和负责人定。

**遗留三，成本只测了 quick 档与一个 standard 样本。**

**下一步 T9：** 对目标仓库所有新 PR 开启只记录模式，跑 5 到 7 天，每天在面板里处置发现，产出一页决策包。这一步的关键判据是**处置比例**（线上主指标），而它需要人的真实反馈，因此 T9 客观上需要真实时间流逝，不是一次会话能完成的。我会先把它需要的东西全部准备好——插件入口、轮询常驻、面板接线——然后把"需要 5 到 7 天"这件事如实标出来。
