# S0 环境与保护（本次只授权执行这一步）

开始前先通读 `docs/design/00-overview.md` 和 `docs/design/01-steps.md`。本步**不改评审逻辑**，只做环境确认、仓库保护和一项安全措施。

## 背景

- 仓库：`https://github.com/Inori-KJT/dsh-review`
- 基线提交：`6bc4b1846837b4c3c712f2b6212344876c8bd10a`（`main` 的当前 head）
- 设计文件由人提交在 `design-v2` 分支上，只包含 `docs/design/` 目录。

## 任务

### 1. 环境报告

写 `docs/reports/S0-env.md`，逐项给出结论和证据（原样贴命令输出）：

| 项目 | 怎么查 |
| --- | --- |
| 操作系统与架构 | `uname -a`、`cat /etc/os-release` |
| Node 与 npm 版本 | `node --version`、`npm --version`。仓库的测试直接运行 `.ts` 文件，需要 Node 支持类型剥离；版本不够时写明，不要自行升级系统 Node |
| git 版本 | `git --version` |
| 访问 GitHub | `git ls-remote https://github.com/Inori-KJT/dsh-review` |
| 访问 GitCode | `curl -sI https://gitcode.com \| head -1`，以及 `curl -sI https://api.gitcode.com \| head -1` |
| 代理设置 | `env \| grep -i proxy`（只写有没有、指向哪个主机，不要贴出可能带密码的完整值） |
| 有没有 DSH | `which dsh`；`ls ~/.dsh`；`npx --no-install @deepseek-ai/dsh --version`。**不要安装 DSH**，只报告 |
| Codex 自身的沙箱是否允许联网和推送 | 实际执行一次 `git ls-remote`，看是否被拦 |

| 能否常驻后台进程 | 说明当前会话结束后，后台进程会不会被杀 |

### 2. 仓库与分支

```bash
cd /mnt/data/zhaochi
git clone https://github.com/Inori-KJT/dsh-review.git   # 已存在则 git fetch --all --tags
cd dsh-review
git config user.name  "codex-agent"
git config user.email "codex-agent@users.noreply.github.com"
```

凭据**不得写入任何文件或 `.git/config` 的远程地址**，只通过环境变量提供：

```bash
git config credential.helper '!f() { echo username=x-access-token; echo "password=$GITHUB_TOKEN"; }; f'
```

然后：

1. 在基线提交上打标签：`git tag v0-baseline 6bc4b1846837b4c3c712f2b6212344876c8bd10a`，再推送这个标签。
2. 从基线开出 `rework` 分支，把 `design-v2` 分支合并进来（只有 `docs/design/` 下的新文件，不应有冲突）。
3. 推送 `rework`。**不向 `main` 推送任何东西。**

### 3. 测试脚本覆盖全部测试

当前 `package.json` 的 `test` 只运行 4 个测试文件，`tests/` 下实际有 9 个。

1. 改成运行 `tests/` 下的全部 `*.test.ts`。
2. 运行 `npm ci` 和 `npm test`，把通过数和失败数记下来。
3. 运行两个类型检查：`npx tsc --noEmit -p tsconfig.json` 和 `npx tsc --noEmit -p tsconfig.pure.json`。
4. 如果之前没被运行的测试现在失败了，**不要修改被测代码**，只在报告里列出失败的测试名和报错，留给后面的步骤处理。

### 4. 可写仓库白名单（总论第 6 节第 8 条）

目标：即使代码有 bug 或配置写错，DR 也不可能写到测试仓库以外的地方。

1. 配置里新增 `writableRepos: string[]`，默认为空数组。
2. 新增一个包装器 `GuardedForge`，实现 `ForgePort`：
    - 读方法（`listPulls`、`getPull`、`listComments`、`readMergeable`、`listReplies`）原样转发。
    - 写方法（`postInline`、`postSummary`、`setStatus`，以及以后新增的任何写方法）只有同时满足两个条件才转发：仓库在 `writableRepos` 里，**并且**本次运行的发布模式不是 `record`。否则抛出 `WriteNotAllowed`，错误信息写明仓库和原因。
    - `setStatus` 的参数里没有 PR 号，同样按仓库判断。
3. 在组装依赖的地方（`src/app/cli.ts` 的依赖创建处，以及 `src/index.ts` 里如果另有组装），把真实的平台客户端一律包在 `GuardedForge` 里。**不允许有绕过包装器直接拿到平台客户端写方法的路径。**
4. 测试（新文件 `tests/guarded-forge.test.ts`），至少覆盖：
    - 白名单为空时，三个写方法全部抛 `WriteNotAllowed`；
    - 仓库在白名单里但模式是 `record`，抛 `WriteNotAllowed`；
    - 仓库在白名单里且模式是 `comment`，调用转发到底层的假平台客户端；
    - 读方法不受影响；
    - 一个结构性测试：`src/` 下除了 `GuardedForge` 和适配器自身，没有地方直接构造 `GitCodeForge`。
