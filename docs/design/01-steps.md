# 步骤概要 S0 到 S11

这里只写每一步的目标和验收标准，让执行者了解全貌。**执行时只做被授权的那一步**，详细指令见 `docs/design/steps/Sn.md`，每次只会提供一份。

每一步都必须满足三条才算完成：

1. 全部测试通过，并且新增了能证明本步完成的测试；
2. 用真实数据或注入缺陷的数据跑一遍，原始输出贴进报告；
3. 提交到 `rework` 分支，打标签 `step-Sn-done`。

| 步骤 | 目标 | 验收标准（概要） | 依赖 | 需要人参与 |
| --- | --- | --- | --- | --- |
| S0 环境与保护 | 报告运行环境；打基线标签；开 `rework` 分支；`npm test` 覆盖全部测试；实现可写仓库白名单 | 环境报告每项都有结论；白名单拒绝非白名单仓库的写操作 | 无 | 提供令牌；保护 `main` |
| S1 修致命缺陷 | F1 审查会话拿到 diff、PR 意图和判据；F2 在 PR 版本的只读 worktree 里审；F3 投票规则改为"展示"和"阻断"分开；F4 核实结果按发现编号对号 | 每条都有测试；注入缺陷集每个用例跑 3 次，能稳定报出 | S0 | 真实运行需要 DSH 环境 |
| S2 状态模型 | 审查记录、运行状态、发现状态、PR 结论按总论第 4 节实现；失败重试；轮次只统计机器人修复；人工重新评审 | 场景表全部通过（3 轮用完后人推送仍会审、DR 失败为 `review_failed`、新 head 让旧记录被取代、裁决只解除对应发现） | S1 | 无 |
| S3 效果基线 | 建缺陷集（用 SZZ 方法从修复提交反查）、干净集、注入集；跑出四项指标 | 基线报告；和人约定底线 | S2 | 确认缺陷来源；约定底线 |
| S4 平台实验 | 在测试仓库实测总论第 8 节的各项能力 | 每项都有"能、不能、部分能"的结论和证据 | 无，可与 S1 到 S3 同时进行 | 在 GitCode 上操作 |
| S5 平台层与门禁 | 能力声明；门禁策略；GitCode 写操作；查询当前 head 结论的接口（带鉴权）；GitHub 适配器 | 两个平台适配器通过同一套契约测试；门禁只认 DR 的记录 | S3、S4 | 无 |
| S6 测试仓库端到端 | 一个人写的 PR、一个 SA 写的 PR，各走完 P5 → P7 → P8 | 旧版本的通过结论不能放行新提交；DR 宕机时状态明确；机器人无权合并；轮次用完后人仍能推进；被扣下的发现在 PR 上可见 | S5 | 人参与审批与裁决 |
| S7 接入 SA | 读取发现的接口校验 head 和授权；SA 补丁文件（机器人名单、提示词、绑定后补读）；人写的 PR 需委派 | 机器人的评论不会唤醒已结束的工单；先发布后绑定也能补读 | S6 | 在测试环境部署 SA 补丁 |
| S8 通用入口 | MCP 入口；CLI 可执行文件；接口文档；`AgentRunner` 的其他实现保持可插拔 | Codex 通过 MCP 发起评审、读取发现，DR 代码零改动 | S6 | 无 |
| S9 面板与参数 | 配置页（版本对比、回滚）；裁决必须写理由；扣下项清单；重新评审按钮；显示批准状态 | 在面板改参数，下一次运行确实用上了新版本 | S6 | 无 |
| S10 提交前自审 | 只接收 git bundle 的 preflight 入口，带限次 | 未推送的提交能被审到；调用方目录审前审后不变 | S7 | 决定是否改用导师在 SA 内部的方案 |
| S11 试运行 | 一个真实仓库，按"只记录 → 发评论 → 阻断"逐档放开 | 每周的指标报告 | 全部 | 导师决定每一档何时放开 |
