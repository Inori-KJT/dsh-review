# dsh-review 设计总论 v2

本文件是 `rework` 分支上所有工作的依据。与仓库里更早的文档（`docs/architecture.md`、各 `t*-report.md`）冲突时，以本文件为准。

配套文件：

- `docs/design/flow-v2.mmd`：完整流程图（Mermaid）。节点编号如 `f10`、`g2` 可在代码注释里引用，便于对照。
- `docs/design/01-steps.md`：S0 到 S11 的步骤概要与验收标准。
- `docs/design/steps/Sn.md`：当前授权执行的那一步的详细指令。**只做被授权的那一步。**

## 1. 目标与边界

DR（dsh-review）是团队公共的代码评审能力。它做三件事：

1. 对仓库里所有 PR 做独立评审，不论作者是人还是 SuperAgent（SA）。
2. 为每个 PR 的当前版本生成一条可追溯的审查记录，供平台门禁判断能否合并。
3. 为调用方（SA、Codex、CI、人）提供提交前自审和结构化发现的读取接口。

DR **不做**：合并、推送代码、替代人的审批、修改 SA 的代码。给 SA 的改动只以补丁文件的形式放在 `docs/superagent-patch/`。

## 2. 四个角色

| 简称 | 角色 | 职责 |
| --- | --- | --- |
| U | 人 | 提需求、裁决争议、审批 PR、批准配置上线 |
| SA | SuperAgent | 实现与修复代码；按 DR 的结构化发现修改 |
| GH | 代码平台（当前是 GitCode，也要支持 GitHub） | 承载 PR、评论、流水线、分支保护；真正执行门禁 |
| DR | dsh-review | 独立评审、保存证据与审查记录、发布评论与结论 |

## 3. 架构

依赖只能从上往下，`core` 不做 I/O，也不 import 任何 `@deepseek-ai/*` 包。

| 层 | 目录 | 内容 |
| --- | --- | --- |
| 外壳 | `src/index.ts`（DSH 插件外壳）；以后可加独立服务外壳 | 只负责组装与生命周期 |
| 入口 | `src/app/`（轮询、Webhook、HTTP、CLI；以后加 MCP） | 把外部请求变成对 Scheduler 的请求 |
| 调度 | `src/app/scheduler.ts` | 运行状态的唯一写入者 |
| 流水线 | `src/core/` + `src/stages/` | 阶段顺序写死在代码里；模型只在阶段内部做判断 |
| 端口 | `src/core/ports.ts` | `ForgePort`、`VcsPort`、`AgentRunner`、`StorePort`、`Notifier` |
| 适配器 | `src/adapters/` | GitCode、GitHub、git CLI、DSH 会话、SQLite 等 |

**宿主无关**：起 agent 会话只通过 `AgentRunner`。现在的实现是 DSH 会话，以后可以加 Codex 运行器或直接调模型 API 的运行器，`core` 和 `stages` 不改。

**平台无关**：平台差异全部放在适配器里，并通过"平台能力声明"（见第 8 节）告诉上层能做什么。

## 4. 核心概念

### 4.1 审查身份与审查记录

- **审查身份**：`(repo, pr, base_sha, head_sha)`。同一身份只做一次正式审查。
- **规则版本**（配置版本号）记录在审查记录里，**但不放进身份**。改配置不会自动重审所有 PR，是否重审由人决定。
- **审查记录**：每次正式审查一条，字段至少包括：身份、规则版本、运行状态、轮次、触发来源、各发现的状态、推导出的结论、被哪条更新的记录取代。

### 4.2 运行状态

`queued` → `running` → `done`，或者 `failed`（自动重试 2 次后仍失败）、`cancelled`。PR 有了更新的 head，旧记录标为 `superseded`。

### 4.3 触发来源

| 来源 | 说明 | 是否计入"机器人修复轮次" |
| --- | --- | --- |
| `pr_opened` | PR 新建 | 否 |
| `bot_fix_push` | SA 根据 DR 发现修复后推送 | **是** |
| `human_push` | 人推送的新提交 | 否 |
| `rebase` | 变基产生的新 head | 否；变基后做**全量**重审 |
| `manual` | 人在面板或 CLI 点"重新评审" | 否 |

### 4.4 发现的状态

| 状态 | 含义 | 是否阻断合并 |
| --- | --- | --- |
| `candidate` | 刚提交，未核实 | 否，不发布 |
| `rejected` | 核实为不成立 | 否 |
| `unverified` | 预算或席位不足，未完成核实 | 否，不发布，只在面板可见 |
| `shown` | Nit 有 1 票成立；或 Important 有 1 票成立且无否决 | **否**，以"建议"发布 |
| `blocking` | 仅限 Important：2 票成立（第二票尽量用另一个模型）且无否决 | **是** |
| `held` | 安全类 Important、改了评审规则文件 | **是**，等人裁决 |
| `awaiting_adjudication` | SA 在线程里写理由拒绝修 | **是**，等人裁决 |
| `dismissed` | 人裁决为误报或有意为之，**必须写理由** | 否 |
| `resolved` | 在之后的 head 上确认已修复 | 否 |
| `stale` | 所在行在新 head 上被改动，待复核 | 复核前保持原阻断性 |

### 4.5 PR 结论（由运行状态和发现状态推导，不单独存）

| 结论 | 条件 | 门禁 |
| --- | --- | --- |
| `pass` | 当前 head 的记录 `done`，且没有阻断性发现 | 放行 |
| `needs_fix` | 有 `blocking` 发现 | 拦 |
| `needs_human` | 有 `held` 或 `awaiting_adjudication`，或机器人修复轮次已用完 | 拦 |
| `review_failed` | 当前 head 的记录 `failed` | 拦 |
| `missing` | 当前 head 没有记录，或仍在运行 | 拦 |

**门禁只认 DR 对当前 head 的记录**，不信 PR 上任何人都能写的状态文本。

## 5. 不变量（必须在代码里强制，每条都要有测试）

1. 只有新 head 或人的 `manual` 请求会创建正式审查；评论、回复、线程关闭永远不触发审查，只写入反馈。
2. 同一审查身份只审一次；重复请求返回已有记录。
3. 机器人修复轮次（`bot_fix_push`）每个 PR 最多 3 轮；用完后结论为 `needs_human`。**人的推送和 `manual` 不受轮次限制**，所以流程永远能被人推进，不会死锁。
4. 第 3 轮起只报 Important。
5. 同一指纹在未解决状态下不重复发布；`dismissed` 的指纹以后不再报；`resolved` 的指纹若在新 head 上再次被发现并核实，作为新发现发布，并记录 `reopened_from`。
6. DR 忽略自己的账号和配置中机器人名单里账号的评论。
7. 提交前自审：同一分支每小时最多 2 次，同一 head 只审一次；结果只返回给调用方，永远不写 PR、不产生触发。
8. 同一 PR 24 小时内正式审查超过 6 次，暂停该 PR 的自动审查，转为 `needs_human`。
9. 预算耗尽时，未核实的发现记为 `unverified`，运行记为 `done` 但带"部分完成"标记，结论不可能是 `pass`，除非人裁决。
10. SA 写理由拒绝只会让发现变为 `awaiting_adjudication`；只有人能把发现改为 `dismissed`。
11. DR 没有推送和合并权限；任何对平台的写操作都要经过"可写仓库白名单"。
12. 变基产生的新 head 做全量重审。

## 6. 安全

1. 审查会话的工作目录是按 sha 建的**只读** worktree，运行结束（包括失败、取消）一律删除。
2. 审查会话只有读文件、列目录、文本搜索、只读 git 这几种工具；没有任意 shell，没有网络。所有路径规范化（含符号链接）后必须落在本次运行允许的根目录内。
3. 评审规则文件（`AGENTS.md`、`REVIEW.md`、`.dsh-review/`）只从 **base** 读取；PR 修改这些文件时生成一条 `held` 发现。
4. 发现里的代码引用只收 `{path, startLine, endLine}`，原文由引擎从 worktree 取出，不接受 agent 自己贴的代码。
5. 任何内容离开引擎之前（发到 PR、返回调用方、写日志、以后的 WeLink）都要经过 `sanitize`；命中密钥特征的发现置为 `held`，被拦内容不写日志。
6. 机器人凭据只存在于宿主进程的配置里，不进入审查会话的环境变量。
7. 提交前自审只接收 `git bundle`，不接受调用方给的任意本机路径。
8. **可写仓库白名单**：平台写操作只允许发往白名单内的仓库，而且只有发布模式不是"只记录"时才允许。白名单默认为空。

## 7. 与 SA 的约定

1. PR 评论只用来**通知**；SA 根据 DR 接口返回的结构化发现行动。
2. 读取发现的接口要求调用方给出 `repo`、`pr`、`head_sha`；head 不是当前 head 时返回"已过期"，不返回旧发现。
3. SA 把工单绑定到 PR 之后，应主动读取一次当前发现，补上绑定之前已发布的结果（防竞态）。
4. 人写的 PR：发现默认交给作者；只有作者或负责人在 PR 里显式委派，SA 才接手。
5. 给 SA 的改动（机器人名单、提示词、环境变量）只作为补丁文件放在 `docs/superagent-patch/`，不直接修改 SA 仓库。

## 8. 平台差异

每个 `ForgePort` 适配器声明自己的能力，上层据此选择门禁策略：

```ts
interface ForgeCapabilities {
  requiredCustomStatus: boolean   // 自定义提交状态能否设为合并必需项
  pipelineGate: boolean           // 能否通过"流水线通过才能合并"做门禁
  inlineComments: boolean
  resolveThreads: boolean
  webhookOnPush: boolean          // 推送新提交是否触发 webhook
  approvalResetOnPush: boolean    // 新提交是否重置已有审批
  requireUpToDate: boolean        // 能否要求基于最新主干（如半线性合并）
}
type GateStrategy = 'status' | 'pipeline'
```

- GitHub：可以直接把提交状态或检查设为必需项。
- GitCode：公开文档只写了"流水线运行通过才能合并"，没有写自定义状态能否作为必需项，也没写新提交是否重置审批。这些在 S4 实测后填入能力声明。门禁默认按 `pipeline` 设计：流水线带着当前 head 向 DR 查询结论。

## 9. 度量

| 指标 | 用途 |
| --- | --- |
| 处置比例（成立、误报、有意为之、不重要、未处置） | 线上主指标，反映噪声 |
| 已知缺陷命中率（缺陷集、注入集分别计算） | 比较两版配置，是相对指标 |
| 干净 PR 上的阻断性误报数 | 衡量会造成有害修改的噪声 |
| 成本与延迟（会话数、token、耗时）、人工处理时间 | 校准预算 |

新配置上线条件：**每一项都不低于事先约定的底线**，不是"总分上升"。

## 10. 给执行 agent 的工作约定

1. **一次只做一步。** 只执行 `docs/design/steps/` 里被授权的那一步。做完写报告，然后停下，等下一步的指令。
2. **分支**：所有提交都在 `rework` 分支上。不向 `main` 推送；每步完成后打标签 `step-Sn-done`。
3. **测试**：`npm test` 必须运行 `tests/` 下的全部测试。每一步都要新增能证明本步完成的测试。
4. **真实输出**：除了测试，每一步都要用真实数据或注入缺陷的数据跑一遍，并把**原始输出**贴进报告，不只写结论。
5. **不得放宽**：防循环不变量、预算上限、安全规则只能加强，不能为了让测试通过而放宽。需要放宽时停下来问。
6. **外部接口与文档不一致时**（DSH、GitCode、GitHub），把现象写进报告并停下来问，不要猜，不要绕过。
7. **凭据**：令牌只从环境变量读取，不写进任何文件、提交、日志或 `.git/config`。
8. **平台写操作**：只允许发往白名单里的测试仓库。
9. **不修改 SA 仓库。**
10. **报告**：写到 `docs/reports/Sn-report.md`，固定包含以下几节：
    - 做了什么（按文件列出）
    - 测试结果（命令与通过数）
    - 真实运行（命令与原始输出）
    - 没做的和原因
    - 发现的问题与需要人决定的事
11. **提交信息**：`Sn: <一句话说明>`，正文写验证方式。
