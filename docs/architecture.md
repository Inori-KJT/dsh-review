# dsh-review 架构说明

本文按两个视角讲同一套东西：**结构视角**回答"有哪些零件、各自归谁管"，**流程视角**回答"一次评审从哪儿开始、经过谁、到哪儿结束"。每一环都回答四个问题：什么条件下被调用、做完什么、代价多少、出问题谁兜底。

---

## 一、这套东西在解决什么问题

在讲结构之前先说清目标，否则后面的取舍看不出理由。

一个团队提交合并请求之后，需要有人读一遍改动，指出两件事：这段代码会不会在某种输入下出错；这次改动有没有引入安全问题。人做这件事有两个困难。**第一个困难是量。** 改动越多，读得越粗，漏得越多。**第二个困难是重复。** 同一类问题会在不同请求里反复出现，每次都要人重新指出一遍。

所以这套东西的目标不是"替代人评审"，是**把容易漏且容易重复的那部分先过一遍，让人只看真正需要判断的部分**。

这个目标决定了一个关键取舍：**它宁可少报，不可乱报。** 乱报会把人的注意力耗在假问题上，结果比不报更糟——人一旦开始怀疑每一条，就会整体不看。因此后文你会反复看到同一件事：每一环都在压数量，而不是在扩数量。

---

## 二、结构：五层，每层只做一件事

代码分五层，依赖方向是单向的。这个方向不是风格问题，它决定了**哪一层可以脱离其他层单独测试**。

```
prompts/        判据：写给模型看的规则
src/core/       规则本体：不依赖任何外部，可脱离一切单测
src/stages/     九个阶段：把规则串成流程
src/adapters/   四类外部：会话、平台、仓库、数据库
src/app/        装配与服务：调度、面板、评测、决策
```

### 2.1 `src/core`：规则本体

这一层是纯逻辑，不读文件、不联网、不调模型，连 Node 的类型定义都不需要。判据是它的类型检查可以在完全不给任何运行时类型的情况下通过——这一点有自动化测试守着。

它包含七样东西：领域类型总表（`model.ts`）、六个端口（`ports.ts`）、阶段接口（`stage.ts`）、阶段顺序与档位（`pipeline.ts`）、预算记账（`budget.ts`）、八条防循环不变量（`invariants.ts`）、指纹与脱敏（`fingerprint.ts`、`sanitize.ts`），以及把阶段串起来的编排（`run.ts`）。

**为什么要把这一层抽出来。** 因为它是唯一"改错了不会报错、只会静默出错"的地方。指纹算错会让去重失效，脱敏漏一条会让凭据发出去，不变量写错会让系统来回空转。这类错误在集成环境里极难复现，所以必须能把它们拉到单测里逐个打。

### 2.2 `src/stages`：九个阶段

九个阶段分成三组。**确定性组**五个（收集、定档、去重、分类、过滤），不调模型，同样的输入永远得到同样的输出。**代理组**两个（找问题、核实），会起真实会话。**人机交界**两个（人闸、记录）。

这个划分的意义在于：**只有两个阶段的结果是不确定的。** 其余七个阶段的行为完全可复现，因此可以放心单测；而系统的不确定性被限制在两个点上，调试时知道该盯哪儿。

### 2.3 `src/adapters`：四类外部接口

外部世界有四类：DSH 的会话接口、GitCode 的平台接口、git 命令行、SQLite。每一类都有且只有一个实现文件，都实现 `core` 里定义的接口。

**为什么要隔这一层。** 因为 `core` 与 `stages` 不许直接碰外部。这样做的直接好处是：把模型换成别的、把 GitCode 换成 GitHub、把 SQLite 换成别的存储，都只改一个文件，不动流程。间接的好处更重要——测试可以用假件替代外部，于是 156 个测试里绝大多数不需要网络也不需要模型。

### 2.4 `src/app`：装配与服务

这一层把上面几层装起来，并对外提供四种东西：调度器（运行状态的唯一写入者）、轮询触发器（发现新提交）、HTTP 与面板（给人看和点）、评测与决策（出基线报告）。

**为什么叫"唯一写入者"。** 运行状态有七个字段会变（状态、游标、轮次、用量等），如果面板、轮询、崩溃恢复各自去改数据库，三方同时改就会写坏。所以规定只有调度器能写，其余三方只能向它发请求。这条规定是崩溃恢复能成立的前提。

### 2.5 `prompts/`：判据

三份 Markdown：正确性审查、安全审查、核实。每份都明确写了三栏——**看什么信息源、什么算一条发现、明确不管什么**。

第三栏最关键。模型在没有边界时会倾向于多报，而多报会把人的注意力耗光。所以每份提示词都用相当的篇幅说"这些不要报"。

## 三、流程：一次评审经过十个环节

一次评审从"某个提交发生变化"开始，到"发现进入面板或抛异常"结束。十个环节里有三个会消耗钱和时间（找问题、核实），其余七个要么是纯计算，要么是等人。

### 3.1 触发：什么情况下开始一次评审

**条件。** 轮询发现某个开放合并请求的 head 提交与库里记录的任何一次都不同。手动发起、命令行发起也算，但判断依据相同。

**做什么。** 创建一条运行记录，写入仓库、PR 号、base 提交、head 提交、轮次、档位。同一个 head 第二次请求时直接返回已有运行，不新建。

**兜底。** 三条不变量在这里生效：同一提交只评一次；评论与回复永远不触发评审（代码上根本没读评论）；同一 PR 24 小时内超过六次就熔断，不再自动评。

**为什么评论不触发。** 因为评审引擎自己会在未来往 PR 上写评论。如果评论能触发评审，就形成"评论→评审→评论"的自环，会一直转下去，烧钱且刷屏。

### 3.2 收集：把这次改动取回来

**条件。** 评审开始后的第一步，无条件执行。

**做什么。** 比较 base 与 head 两个提交，拿到改动文件清单、每个文件改动的行范围；再从 **base 版本**读 `AGENTS.md` 与 `REVIEW.md` 这两份仓库级规则文件；如果被评审的这次改动本身动了这两个文件，就立即生成一条"需人工确认"的发现并扣下。

**代价。** 一次 git 差异计算，实测在中等仓库上约一秒以内。不消耗模型。

**兜底。** 规则文件只从 base 读，绝不从 head 读。因为如果一个请求可以顺手改掉评审规则，它就能写一句"本目录不审安全问题"把自己放过去。这一条在测试里有断言。

### 3.3 定档：决定花多少力气

**条件。** 收集完成后执行。

**做什么。** 按改动量选择档位。改动超过 1500 行或 40 个文件时**不升档**，反而只挑最重要的文件审，其余在报告里列为"未评审"并建议拆分。

**为什么反着来。** 直觉是改动越大越该仔细看，实际相反：一个改动越大的请求，评审越容易在没有重点的情况下烧掉预算却什么也说不清。挑重点并明确说"其余没看"，比假装全看了更诚实。

### 3.4 找问题：唯一真正"看懂代码"的环节

**条件。** 定档完成后，按档位起一或两个只读会话。quick 档一个（只查正确性），standard 档两个（加安全检查）。

**做什么。** 每个会话拿到一份判据文件、一个工作目录、一组只读工具，自己翻文件、追调用链，最后通过一个专用工具提交发现。发现必须带齐五样：位置、一句话结论、触发条件、错误结果、是否本次引入。缺触发条件或错误结果的，工具直接拒收。

**成功率。** 这一环的准确率**目前没有可靠数据**。已有的三个观察点是：

- 注入的循环越界缺陷：两次运行都找到，且触发条件与错误结果都写准了
- 注入的路径穿越缺陷：第一次找到，第二次没找到
- 我第一次做的玩具仓库（真实写法）：找到，并给出了准确的崩溃原因

所以能确定的只有一件事：**它能找到明显缺陷，但同一缺陷不保证每次都找得到。** 具体准确率需要更大样本，我没有。

**代价。** 实测 quick 档单次 15 到 39 秒、1 到 2 个会话、1 到 2 个回合。standard 档在真实请求上一次跑了 376 秒。**token 数取不到**，因为宿主不提供单会话的 token 统计。

**兜底。** 三层。第一层是会话本身的限制：只读工具、无 shell、无网络、工作目录之外一律拒绝，所以它即使想乱来也改不了东西。第二层是提交工具的参数校验，缺字段就拒收。第三层是后面的去重与核实。

### 3.5 去重：把同一个问题认成同一个

**条件。** 所有审查会话结束后执行。

**做什么。** 先按"路径 + 行号 + 类别"合并完全同位置的重复；再给每条发现算一个指纹，指纹由路径、所在符号、类别、规范化后的代码、同一符号内的序号五样算出。然后丢掉两类：库里本 PR 已存在且未解决的同指纹发现，以及已被人判为误报或有意为之的同指纹发现。

**兜底。** 指纹**不含行号**，所以代码上下移动几行不会让它变成新问题。这是"已判误报的以后不再报"能生效的前提。

**代价。** 纯计算，毫秒级。

### 3.6 核实：让另一群会话逐条怀疑

**条件。** 有候选发现时才执行；quick 档只有一个核实席位，standard 档有两个。

**做什么。** 把候选按文件就近分组，每批最多五条，交给独立的核实会话。核实会话**看不到审查会话的推理过程**，只看到那条发现的结构化字段，然后自己读代码验一遍。它必须回答三选一（成立/不成立/不确定），并且必须回答"这个问题在 base 版本上是否同样存在"。

**投票规则。** Nit 一票成立即可；Important 需要两票成立且没有人说不成立；任何一票说不成立就否决；"不确定"不发布。

**为什么让另一群会话去怀疑。** 因为在同一段推理里自我检查的准确率很低。换一个会话、只看结论、重新推一遍，才有独立性。

**代价。** 与找问题同量级。standard 档可能用到四个核实会话。

**兜底。** 这是压制误报的主要手段。此外还有一层：只有"重要、已被判成立、且没人说不成立"的发现才会触发第二次独立投票——这就是"Important 需两票"能成立、又不必每条都花两票的原因。

### 3.7 分类：判断是不是本次引入

**条件。** 核实之后执行。

**做什么。** 判断每条问题是不是本次改动引入的。只有三个条件同时成立才判为"既有问题"：命中的行不在本次差异里；审查会话自己说不是本次引入并给了理由；核实会话在 base 版本上确认同样成立。任一条不满足，一律按本次引入处理。

**为什么这么保守。** 因为两类误判的代价不对等。把旧问题误判为新问题，代价是作者会反驳一句，可以接受。把新问题误判为旧问题，代价是真问题被当成旧账放过，后果由线上承担。

**兜底。** 另有第三轮之后只报重要问题的规则，也在这一步生效。

### 3.8 过滤：压数量

**条件。** 分类之后执行。

**做什么。** 丢掉落在"未评审路径"里的发现；同一次评审里 Nit 最多留三条；抽掉严重度不在本轮范围内的。

**代价。** 纯计算。

**兜底。** 这一环不产生新信息，只做减法。减错了会让真问题消失，所以它的规则写得非常窄——只按路径与数量，不按"看起来重不重要"。

### 3.9 人闸：把判断交给人

**条件。** 有通过核实的发现时执行。quick 档不设这一关，standard 档设。

**做什么。** 安全类的重要问题、以及改动规则文件的问题，**无论闸门开不开都一律扣下**等人确认；其余发现进入"等你处理"栏。人可以在面板上把每条标成四类之一：成立、误报、有意为之、不重要。

**为什么这两类永远扣下。** 因为这两类错了的代价不对等：前者可能放过漏洞，后者能让规则被悄悄改掉。

**兜底。** 人的判断会写进库，并直接影响下一轮：判误报的问题下一轮不再报。也就是说**人的时间只花一次**，不会重复花在同一个问题上。

### 3.10 记录：只落库，不发出

**条件。** 最后一步，无条件执行。

**做什么。** 把结果的形态整理好——以问题计数开头的摘要、带隐藏指纹标记的行内正文——但**不向平台发任何东西**。发出前还有一道脱敏扫描：私钥头、常见令牌前缀、高熵串、内网地址、家目录路径，命中就扣下并记一条安全事件。

**为什么连发都不发。** 见下一节。

## 五、九条防线：某一环失效时谁接住

这张表回答"如果这里错了，会不会导致灾难"。**九条防线里只有三条依赖模型，其余六条是代码。**

| 如果这里错了 | 谁接住 | 依赖模型吗 |
|---|---|---|
| 模型漏掉了真问题 | 没有人接住；这是已知的能力上限 | — |
| 模型报了假问题 | 核实会话投票否决 | 是 |
| 模型报了重复问题 | 指纹去重 | 否 |
| 模型把旧问题说成新问题 | 分类三条件 | 否（第三条件要核实会话） |
| 模型读到了不该读的文件 | 路径围栏先拒，脱敏再拦 | 否 |
| 模型把敏感内容写进发现 | 发布前脱敏扫描 | 否 |
| 模型陷入无效循环 | 预算上限、轮次上限、熔断 | 否 |
| 引擎自己的评论触发下一轮 | 触发器不读评论 | 否 |
| 进程中途崩溃 | 调度器从游标恢复 | 否 |

**这九条里唯一没有兜底的是第一条。** 漏报无法被系统内部发现，只能靠事后出事反推。这也是为什么决策包把"处置比例"当主指标而不是把"命中率"当主指标——处置比例来自人，人能看到系统漏掉的东西。

## 六、协同：为什么这样组合能得到可用的结果

单看每一环都不强。找问题会漏也会错，去重只认指纹，核实也只有三票。**这套东西的价值来自它们相互抵消误差的方式。**

**第一层抵消：把"报得多"变成"报得准"。** 找问题容易多报，核实专门否决，两层之后留下来的通常是能说清触发条件的。实测里干净代码上是 0 条发现，说明这一层起作用了。

**第二层抵消：把"每次都要重说"变成"只说一次"。** 指纹让同一个问题跨轮次被认出来，人的处置又会把那些问题永久静音。于是**人花在一个问题上的时间只花一次**——这是这套设计里对注意力最友善的一条。

**第三层抵消：把"模型不确定"隔在两个点上。** 九个阶段里只有两个用到模型，其余七个完全可复现。所以出了问题能二分：如果同样的输入两次得到不同的发现，问题在模型；如果同样的输入两次得到不同的筛选结果，问题在代码。**这一条让调试有方向。**

**第四层抵消：把"可能乱来"关在笼子里。** 会话只有只读工具、没有 shell、没有网络、路径越界一律拒绝，发布前还有一道脱敏。三层叠加的意义不是"相信模型会守规矩"，而是"即使它不守规矩也改不了东西、发不出去"。

**所以它生产的是这样一类任务结果：** 一个改动进来，出来一批**带位置、带触发条件、带错误结果、经过独立核实、按本次引入与否分过类、被压过数量**的问题清单，附上每条问题在面板上等人的一句判断。它的质量上限由模型决定，质量下限由那六条不依赖模型的防线决定。

## 七、现在的质量：哪些有数字，哪些没有

**有数字的（实测）：**

- 自动化测试 156 条通过；领域逻辑在零运行时类型下通过类型检查
- 真实仓库的两个开放合并请求上跑完整条流水线，结果落库
- quick 档单次找问题：15 到 39 秒、1 到 2 个会话、1 到 2 个回合
- standard 档在真实请求上：376 秒、0 条发现
- 注入缺陷的命中：同一批用例连跑两次，一次 2/2，一次 1/2
- 干净用例上的误报：0 条（样本 1 个）

**没有数字的（未知）：**

- 真实代码里的真实缺陷命中率
- 真实代码上的误报率
- token 成本
- 跨多次运行的方差究竟多大

**结论一句话：它能跑，但"能审出多少真问题、报错多少"目前没有依据。** 唯一能填这个空的办法是跑一段观察期，拿真实处置数据。这件事需要墙上时间和人的判断，不是写代码能解决的。

---

## 八、代价花在哪里

按消耗量排，这笔账在意的是三样东西。

**钱。** 只花在找问题与核实两个环节。quick 档一次两个会话，standard 档一次最多六个。这是主要成本，也是唯一能通过改档位控制的成本。**具体金额我不知道**，因为 token 数取不到。

**时间。** quick 档几十秒，standard 档几分钟。落在人的等待上不成问题，因为它是后台跑的；落在轮询上要注意别把间隔设得太短，否则会在同一批请求上反复触发——不变量会挡住，但会白花一次平台调用。

**人的注意力。** 这是最贵的一项，也是所有设计取舍的起点。压数量、两票制、指纹静音、人闸只放需要判断的——这些都在保护同一件东西：**让人只看值得看的那几条。**
